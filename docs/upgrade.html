Why hasn't it switched yet?

–

The rule: the network switches only when every block keeper in the set announces exactly the same step (for example 1.0.7->1.0.8). There is no percentage threshold – 98 % is not enough, a single keeper that still announces only the old version holds everyone back. This is in the node code: the version state moves on only if descendant_bk_set … protocol_support … all_elements_same() (block_processor/service.rs, block_protocol_version_state.rs).

  1. Announce: an operator installs the new node. Its keeper announces the new version only when its own epoch ends and continues (the value comes from the keeper's epoch contract).
  2. All the same: as soon as all keepers announce the same step, the next block locks the transition.
  3. Switch: once that block is finalized, the whole network runs the new version – a matter of minutes, not hours.

So the remaining keepers decide when it happens. If their operators have already installed the new node, the switch comes right after the last of their epochs ends. If not, it waits until they update – or until they leave the set. A new keeper that joins with the old version would hold it back again.

When block keepers can switch

Every block keeper has its own epoch of about 24 h, and the ends are spread over the whole day. A keeper can only announce a new version at the end of its epoch. The chart shows how many block keeper epochs end in each hour from now.
Not the same as the mining epoch (5.5 min) or the 24-h mining day with the daily tap limit – those run on their own clock.
